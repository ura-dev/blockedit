# 計測ハーネス

`blockedit.py` を速く・正しくできるかを実測するための道具。モデルやサーバ構成を替えて
同じ負荷を回し、**速度と品質を必ず両方見る**。

本番のロジックは複製せず、`blocks.py` / `gates.py` / `client.py` / `task.py` を
そのまま import する(`_parent.py` が親を import path に載せる)。プロンプトの組み立て・
サンプラ設定・出力の掃除が本番と1バイトでも違うと、計測が本番を代表しなくなる。

**振れるのはここだけ。**`UNIT` / `SCOPE` は本番では安全境界としてタスクファイルに
固定されているが、測るには振れないと困る。分けてあるのはそのため。

KoboldCpp が `http://127.0.0.1:5001` で起動していること。出力は `out/` と
`results/`(git管理外)。

**計測対象は `targets.json` で宣言する**(git管理外。雛形は `targets.example.json`)。
どのリポジトリのどの文書を負荷に使うかはベンチのソースに書かない — 手元に無いパスを
指したまま配られるし、そのリポジトリの構成が公開物に残るため。設定が無ければ
計測せずに落ちる。

## 行スコープの負荷

```
uv run python chunk_probe.py          # 1リクエストに詰める行数を振る
uv run python concurrency_probe.py    # 同時実行数・エンドポイントを振る
uv run python sampler_probe.py        # DRYの有無を振る
```

共通の負荷は `targets.json` の `task` が指すタスクファイル(見本は
`tasks/example_heading_labels.py` の見出し分類)。`validate` が
常に非Noneを返すためファイルに一切書き込まず、何度でも安全に回せる。1行1リクエストの
結果が `out/baseline_1line.txt` に基準として残り、以降の条件はこれとの一致率で評価される。
**モデルを替えたら基準も取り直すこと**(`chunk_probe.py` を chunk=1 込みで回せば自動で上書き)。

見出し分類は**小型モデルに最も不利な形状**(本文なしの見出し単独で抽象分類)である点に
注意する。機械的な変換タスクでは順位が変わりうるので、ここでの一致率をモデルの総合力として
読まない。

## ブロックスワップの負荷

ローカルLLMに「ブロックの変更後の全文」を出させ、実ファイルと**バイト比較**する。
正解が1バイト単位で決まるので、モデルやサンプラーを替えたときの良し悪しが一意に出る。

仕掛けは注入。既存の語をリンクで包み(`**語**` → `**[語](path.md)**`)、「リンクを表示
テキストだけに戻せ」と指示する。平坦化した期待出力はpristineな実ファイルと1バイトも
違わないので、**正解判定が実ファイルとのバイト比較になる**。実docは読み取り専用で、
計測ハーネスは `docs/` に書き込まない。

```
uv run python multidoc_swap.py            # 実doc 8本(既定)。汎化と成功率
uv run python multidoc_swap.py --docs 4   # 先に4本で足切り
uv run python section_swap.py --split para --sep blank   # 運用構成と同じ分割で測る
uv run python rewrite_swap.py --trials 3 --temp 0 --sampler nodry   # 単一docで条件比較
uv run python gate_replay.py              # 保存済みの生出力にゲートを後付けで当てる
```

`--sampler` は `dry` / `nodry` / `bare` から選ぶ。実測ではこの3つに有意な差は出ていない。
生出力は `results/raw/` に残る。

## 判定の作法

- **速度だけで採否を決めない。**1行1リクエストの結果と突き合わせ、一致率を必ず出す
- **`exact` 以外は全部失敗。**「だいたい合っている」はこの方式では失敗と同義で、
  差し替えは変更範囲外の1バイトの化けもそのまま確定させる
- 集計は3つを見る。**完全一致**(本命)/ **ゲート素通りの破損**(0でなければゲートの
  設計不足)/ **誤って弾いた正解**(0でなければゲートが厳しすぎる)
- **比較は件数を揃えてから。**途中で1件欠けた列を位置で突き合わせると以降が全部ずれ、
  実態より低い一致率が出る(`_common.agreement` は長さが違えば比較を拒否する)
- **同時実行の検証には対照群を置く。**`--parallelrequests 1` のサーバに同じ同時実行を
  かけ、そちらでも同じ数字が出るならフラグは効いていない
- **サーバは `--nofastforward` を付けて起動する。**外すと同じプロンプトの2回目以降が
  静かに変わり、条件ではなく試行番号を測ることになる。起動スクリプトには恒久で入っている

## ゲートを触ったとき

`gate_replay.py` を回す。**判定の反転が0件であること**が、既存の成績を壊していない根拠に
なる。生きたdocsとの比較なのでdocsを編集すると成績が動く点に注意。入力と期待値を自分で
持つ決定的な検査は本体側の `blockedit_selftest.py`(0トークン・0.1秒)。

## 実測の結論

主要な数値とその経緯は、決まりごとのすぐ隣に置いてある — 本体の `README.md` と
`blocks.py` / `gates.py` / `client.py` の docstring に、どの実測がその設計を決めたかが
書いてある。**同じ実験を繰り返す前にそちらを読むこと。**

新しく回した結果のうち後で参照する価値があるものは `feedback/` に人力で残す
(書き方は `feedback/README.md`)。
